# 套版接口解读

## 1. 这是什么接口？

接口地址：`POST /layout/generate/`

它的作用可以简单理解为：

> 给接口一批大玻璃原片，以及需要切割的小玻璃尺寸，接口帮我们计算“怎么摆放、怎么切割比较合适”，最后返回每张原片上的摆放结果和剩余废料。

这里的“套版”不是排版文字，而是玻璃切割行业里的排版：把多个小玻璃片安排到大玻璃原片上，尽量提高原片利用率，减少浪费。

接口的尺寸示例都是整数，结合当前数据可以按毫米理解。例如：

- `[3660, 2600]` 表示宽 3660 mm、高 2600 mm 的原片。
- `[1120, 1200]` 表示宽 1120 mm、高 1200 mm 的成品玻璃。

> 注意：接口 YAML 没有明确写单位，毫米是根据 mock 数据和玻璃业务数据推断出来的，正式使用时建议和接口提供方确认。

## 2. 一次调用的大致流程

1. 准备原片信息：原片有多大、多少张、什么类型、是否需要修边。
2. 准备成品玻璃信息：每种玻璃有多大、需要多少块、是否为新玻璃。
3. 设置套版规则：最低切裁率、掰片距离等。
4. 调用 `POST /layout/generate/`。
5. 接口返回一张或多张“套版图”。每张套版图对应一张原片上的切割安排。
6. 前端根据 `Position`、`Width`、`Height` 和 `PolygonPel` 把玻璃块和废料画出来。

## 3. 请求参数

请求体使用 JSON，主要分成四部分：套版规则、原片列表、成品玻璃列表、上一次套版结果。

### 3.1 顶层字段

| 字段 | 类型 | 大白话说明 |
| --- | --- | --- |
| `task_id` | string/number | 本次任务的编号。示例里有这个字段，但 YAML 的字段定义区没有列出，建议确认是否为必传。 |
| `min_cutting_rate` | number | 最低切裁率。可以理解为：希望原片至少有多少比例被有效利用。`0` 表示不设置最低要求，`0.95` 表示希望达到 95% 左右。具体是按面积还是其他规则计算，需要接口方确认。 |
| `cutting_margin` | integer | 掰片距离。玻璃之间或切割线需要预留的距离，当前 mock 是 `0`。 |
| `sheet_infos` | array | 可用的大玻璃原片列表。 |
| `glass_infos` | array | 要切出来的成品玻璃列表。 |
| `layout_result` | object/null | 上一次套版结果。用于二次套版，第一次调用通常传 `null`。YAML 标记为必填，但当前请求 mock 没有这个字段。 |

### 3.2 `sheet_infos`：原片信息

每一项代表一种可用于切割的大玻璃原片。

| 字段 | 类型 | 大白话说明 |
| --- | --- | --- |
| `id` | integer | 原片 ID，用来标识这类原片。 |
| `glass_type` | integer | 原片类型。当前示例是 `0`，具体数字代表什么类型需要接口方提供枚举说明。 |
| `size` | integer[] | 原片尺寸，通常是 `[宽, 高]`。例如 `[3660, 2600]`。 |
| `num` | integer | 原片数量。示例中是 `999`，表示最多可以使用 999 张。 |
| `trimming_margin` | integer[][] | 原片四边修边情况。可以理解为四个方向需要修掉或预留多少尺寸。当前示例为四组 `[0, 0]`，表示没有修边。数组每一项具体对应哪个方向，需要与接口方确认。 |

当前请求 mock 中只有一种原片：

- 原片尺寸：3660 × 2600
- 可用数量：999 张
- 原片类型：0
- 修边：全部为 0

### 3.3 `glass_infos`：成品玻璃信息

每一项代表一种要生产的成品玻璃。

| 字段 | 类型 | 大白话说明 |
| --- | --- | --- |
| `id` | integer | 成品玻璃 ID。返回结果中的 `GlassId` 会用它来对应这块玻璃。 |
| `glass_type` | integer | 成品玻璃类型。需要和原片类型匹配时，接口会按类型进行套版。 |
| `size` | integer[] | 成品尺寸，通常是 `[宽, 高]`。 |
| `num` | integer | 需要生产的数量。 |
| `grinding_margin` | integer[][] | 磨边信息，表示四边磨边或预留尺寸。当前示例全部为 0。 |
| `new_glass` | integer | 是否是新玻璃。`0` 表示不是，用于二次套版时区分新增玻璃。YAML 说明默认值为 `0`。 |

当前请求 mock 表示需要切割：

| 玻璃 ID | 尺寸 | 数量 |
| --- | --- | ---: |
| 2096868612367290370 | 1120 × 1200 | 8 |
| 2096868612367290372 | 1120 × 1200 | 8 |
| 2096868612367290374 | 1120 × 1200 | 8 |
| 2096868612367290376 | 680 × 990 | 3 |
| 2096868612367290378 | 680 × 990 | 3 |

这些玻璃虽然尺寸相同，但 ID 不同，所以业务上可能代表不同订单、不同位置或不同玻璃规格，不能只根据尺寸合并处理。

## 4. 返回结果

返回结果的整体结构如下：

```json
{
  "status": 200,
  "data": {
    "Ratio": 0.5567968400071666,
    "SpecPlateAreas": [],
    "Origin": "left_bottom"
  },
  "msg": "套版完成!"
}
```

### 4.1 顶层返回字段

| 字段 | 大白话说明 |
| --- | --- |
| `status` | 接口处理状态。示例中的 `200` 表示处理成功。它是业务返回体中的状态，不一定等同于 HTTP 状态码。 |
| `data` | 套版结果主体。 |
| `msg` | 给人看的处理消息。示例为“套版完成!”。 |

### 4.2 `data` 字段

| 字段 | 大白话说明 |
| --- | --- |
| `Ratio` | 总体利用率或套版比例。示例是 `0.5567968400071666`，换成百分比约为 55.68%。这个字段的精确定义需要接口方确认。 |
| `SpecPlateAreas` | 套版图列表。通常一项代表一张已经安排好切割方案的原片。 |
| `Origin` | 坐标原点位置。示例是 `left_bottom`，表示坐标原点在左下角。 |

### 4.3 `SpecPlateAreas`：每张套版图

每一项代表一块原片的切割方案。

| 字段 | 大白话说明 |
| --- | --- |
| `Ratio` | 当前这张原片的利用率或有效面积比例。示例第一张约 89.84%，第二张约 21.52%。 |
| `Width` | 当前套版区域宽度。示例为 3660。 |
| `Height` | 当前套版区域高度。示例为 2440。注意：请求中的原片高度是 2600，但返回套版区域高度是 2440，可能表示实际可切割区域或修边后的有效区域，建议确认。 |
| `DuplicateMark` | 当前套版图的唯一标记。可以用来区分不同套版方案或不同原片。 |
| `ParentDuplicateMark` | 父级套版图标记。用于表示当前方案是从哪一个方案继续拆分或复制出来的。 |
| `OriginalId` | 对应原片的 ID。 |
| `OriginalType` | 对应原片的类型。 |
| `PelList` | 当前原片上摆放的玻璃块和废料列表。 |

## 5. `PelList`：原片上每一块区域

`PelList` 中既包含成品玻璃，也包含废料。

| 字段 | 大白话说明 |
| --- | --- |
| `Type` | 区域类型。示例中都是 `0`，具体枚举含义未在 YAML 中说明。 |
| `Width` | 这块区域的宽度。 |
| `Height` | 这块区域的高度。 |
| `WasteFlg` | 是否为废料：`0` 表示成品玻璃，`1` 表示废料。 |
| `GlassId` | 对应请求中的玻璃 ID。为 `-1` 时表示这块区域不是成品玻璃，而是废料。 |
| `GlassType` | 玻璃类型。 |
| `Position` | 这块区域的左下角坐标，包含 `X` 和 `Y`。 |
| `PolygonPel` | 这块区域的轮廓。即使是矩形，也通过多条线段描述边界。 |

### 如何判断一块区域是不是成品？

```text
WasteFlg = 0 且 GlassId >= 0：成品玻璃
WasteFlg = 1 且 GlassId = -1：废料
```

例如：

- `Width=990`、`Height=681`、`GlassId=10`、`WasteFlg=0`：表示一块成品玻璃。
- `Width=90`、`Height=681`、`GlassId=-1`、`WasteFlg=1`：表示一块废料。

## 6. 坐标怎么理解？

返回结果中的坐标以 `Origin` 为准。当前 `Origin` 是 `left_bottom`，可以按下面方式理解：

- 原片左下角是 `(0, 0)`。
- `X` 向右增加。
- `Y` 向上增加。
- `Position.X` 和 `Position.Y` 是当前区域左下角的位置。
- `Width` 和 `Height` 是当前区域的尺寸。

例如：

```json
{
  "Width": 990,
  "Height": 681,
  "Position": {
    "X": 990,
    "Y": 0
  }
}
```

表示这块玻璃：

- 左下角位于 `(990, 0)`。
- 右上角大约位于 `(1980, 681)`。
- 占用范围是 `X=990~1980`、`Y=0~681`。

前端绘图时，一般可以把 `Position` 作为绘制起点，再根据 `Width` 和 `Height` 计算显示大小。由于原片尺寸很大，页面上通常需要按比例缩放，而不能直接使用毫米作为像素。

## 7. `PolygonPel` 是什么？

`PolygonPel` 用来描述区域的真实轮廓。它里面有一个 `Lines` 数组，每一项是一条边。

当前 mock 返回的区域基本都是矩形，所以每个区域通常有 4 条 `StraightLine`：

- 一条左边
- 一条上边
- 一条右边
- 一条下边

如果以后出现异形玻璃，可能会出现弧线：

- `StraightLine`：直线边
- `ArcLine`：弧线边
- `Type`：线段类型，具体枚举需要接口方补充

前端如果只需要展示矩形套版图，可以优先使用 `Position + Width + Height`。如果要精确展示异形玻璃或实际切割轮廓，则需要读取 `PolygonPel.Lines`。

## 8. 当前返回 mock 怎么读？

当前返回中有 2 个 `SpecPlateAreas`，可以理解为接口给出了 2 张原片的套版方案：

### 第一张套版图

- 套版区域：3660 × 2440
- 利用率：约 89.84%
- `PelList` 中有成品玻璃，也有废料
- 多块成品玻璃从 `(0, 0)` 开始依次摆放
- 例如前三块 `990 × 681` 的玻璃横向排列在顶部
- `GlassId=-1` 的区域是没有被利用的剩余部分

### 第二张套版图

- 套版区域：3660 × 2440
- 利用率：约 21.52%
- 继续摆放剩余的成品玻璃
- 因为可用空间利用率较低，剩下的大块区域大多被标记为废料

### 为什么总体 `Ratio` 只有约 55.68%？

可以粗略理解为：两张套版图合在一起后，成品玻璃占全部使用面积的比例约为 55.68%。

第一张利用率较高，第二张利用率较低，平均或综合之后，总体比例就会被第二张拉低。具体计算口径不能只根据 mock 反推，需要接口方确认 `Ratio` 是否按面积加权计算。

## 9. 二次套版怎么理解？

YAML 中的 `layout_result` 用于二次套版：

- 第一次套版：没有历史结果，传 `null`。
- 第二次套版：把上一次接口返回的结果传回 `layout_result`，让接口在原有方案基础上继续处理。
- `new_glass=1` 可以用来标记新增的玻璃，`new_glass=0` 表示原有玻璃。

当前 `layout_data_params.json` 是首次套版风格的数据，没有 `layout_result` 字段；如果接口严格按照 YAML 校验，建议补上：

```json
"layout_result": null
```

同时，YAML 示例中包含 `task_id`，但字段定义没有声明它。为了避免请求被校验拒绝，建议确认 `task_id` 是否正式支持，以及它的类型究竟是字符串还是数字。

## 10. 对当前项目接入的建议

服务端拿到接口返回值后，建议保留完整的 `data` 结构，不要只取 `Ratio`。前端至少需要这些字段来画图：

```text
返回 data
  └─ SpecPlateAreas[]             每张原片的套版图
      ├─ Width / Height           套版区域大小
      └─ PelList[]                 玻璃块和废料
          ├─ WasteFlg              成品还是废料
          ├─ GlassId               对应哪块成品玻璃
          ├─ Width / Height        区域大小
          ├─ Position              左下角坐标
          └─ PolygonPel             精确轮廓
```

推荐的前端展示逻辑：

1. 遍历 `SpecPlateAreas`，每项显示一张原片。
2. 使用 `Width` 和 `Height` 设置原片画布比例。
3. 遍历 `PelList`。
4. `WasteFlg=0` 的区域按成品玻璃显示，并展示 `GlassId`。
5. `WasteFlg=1` 的区域按废料显示，可以使用不同颜色或纹理。
6. 需要精确显示异形轮廓时，再解析 `PolygonPel.Lines`。
7. 页面展示时按比例缩放坐标，不能直接把毫米当作 CSS 像素。

## 11. 目前需要接口方确认的地方

以下内容在 YAML 或 mock 中没有定义清楚，正式联调前建议确认：

- 所有尺寸和坐标的单位是否都是毫米。
- `task_id` 是否必传，类型是字符串还是数字。
- `layout_result` 是否必传，首次请求是否必须传 `null`。
- `size` 数组是否固定为 `[宽, 高]`，是否允许旋转。
- `trimming_margin` 和 `grinding_margin` 的四组数据分别对应哪四条边。
- `glass_type`、`OriginalType`、`Type` 的枚举值含义。
- `Ratio` 的计算口径，是单张利用率、面积比例，还是综合利用率。
- 返回的 `Width/Height=3660/2440` 与请求原片 `3660/2600` 不一致的原因。
- HTTP 状态码和返回体中的 `status` 是否都需要同时判断。
- 失败时的返回结构和错误码。

## 12. 一句话总结

这个接口就是：

> 输入“大玻璃原片有哪些”和“要切哪些小玻璃”，接口返回“每张原片上每一块玻璃和废料应该放在哪里”，前端据此画出套版图并展示利用率。
